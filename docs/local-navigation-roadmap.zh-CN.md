# 局部导航路线图（吸收 Project Guideline）

> 状态：**提案，先评审**。这里的内容都还没有实现。每个里程碑在写代码前先作为方案评审，单独成
> 一组 PR 合入；除非里程碑明确说明，否则不改变现有 Guidance 行为。发版没有截止日期，完成一组
> 相互配套的里程碑就发一版。实现细节见
> [`local-navigation-implementation.zh-CN.md`](local-navigation-implementation.zh-CN.md)。

## 1. 为什么做

现在的 Sailens Guidance 回答的是"这一帧看到了什么，值不值得提示"（`SceneSnapshot` →
`SceneEvent` → 语音/震动）。这很适合"前方有人""镜头被挡""前方不通"，但下面这些问题它答不了：

- 障碍物有多远，而且不受手机俯仰角影响；
- 前方地面平不平，有没有台阶或落差；
- Guidance 此刻还有没有资格给出指引；
- 以后：用户该往哪边走。

Google 的 [Project Guideline](https://github.com/google-research/project-guideline)（下称 PG）
补上了中间这一层：空间表示、运动、控制、显式 STOP。它 2026 年的后继项目
[Running Guide agent](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/running-guide-agent/)
把设备端快速安全路径和较慢的 VLM 路径分开。本路线图把这些思想吸收进 Sailens 自己的架构。
这不是移植：不复制 PG 代码，PG 只是参考，不是模板。

目标用一句话概括：

```
感知 → 地面几何 → 局部世界模型 →（之后）规划 → 控制 → 无障碍输出
             SceneEvent 继续并存，负责"发生了什么"
```

## 2. PG 实际做了什么，依赖什么前提

读自 PG `main`（2026-09）。前提比技术本身更重要，因为 Sailens 大多不具备这些前提。

| PG 做法 | 位置 | 依赖的前提 | Sailens 的态度 |
|---|---|---|---|
| 在逆深度空间用 RANSAC 拟合缩放和偏移，把相对深度对齐到公制，至少 10 个内点 | `depth/depth_align_ransac.cc` | ARCore VIO 特征点的公制深度 | **借数学**，锚点换成地平面（重力 + 假设手机高度），不用 VIO |
| 把图像点和固定相机高度的虚拟地平面求交 | `util/hit_test_util.cc`，`camera_height_meters`（默认 1 m，注释写着"待标定"） | 手机固定在腰部背带上；位姿来自 ARCore | **借**：障碍物距离就应该这样算（§5，M3a） |
| 点云 → 重力对齐的通行区占据格（4 m × 5 m，1 m 格，高度带为相机 −0.5…+1.2 m） | `environment/occupancy_map.cc`、`obstacle_utils.cc` | 世界坐标下的公制点云 | **借思路**。但它的高度带丢掉了离地约 0.5 m 以下的一切：**PG 根本不检测路沿、台阶、落差**，Sailens 必须补上 |
| 占据格逐帧计算，不跨帧 | `occupancy_map.h` 注释 | — | **改进**：带新鲜度和衰减的滚动占据 |
| 报"前方有障碍"前做时间滞回（约 30 帧里要 15 帧） | `util/windowed_value_latch.h` | — | Sailens 已有跟踪和冷却；只对新信号复用这个思路 |
| 按 VIO 速度方向导航，低于最小速度才用相机朝向 | `environment/path_planning.cc:53-60` | 公制 6 自由度位姿（ARCore） | 没有 VIO **无法照搬**：手机 IMU 能给可靠的旋转，给不了平移（§6） |
| 丢失跟踪 → 重置 + STOP | `guidance_system.cc` `OnTrackingStateChanged` | — | **借**：失去资格是一种状态，不是一条提示（M1） |
| 低延迟空间音频 | `audio/` | 耳机，固定声音包 | 已在 [`guidance-validation-roadmap.zh-CN.md`](guidance-validation-roadmap.zh-CN.md) C 阶段规划；不移植 PG 声音包和 AAudio |
| Unreal 仿真器 | `unreal/` | — | **借目的，不借工具**：确定性的 JVM 仿真器（M2） |

PG 里不要重蹈的问题：深度对齐失败时点云不刷新，结果是旧点云配新位姿；
`auto obstacle = obstacles.emplace_back()` 做了拷贝，障碍物位置从没被设置（只是因为调用方只用
`empty()` 才没出事）。

模型：PG 的 `depth.tflite` 模型卡写的是 Apache-2.0，训练数据为带 DPT 伪标签的 OpenImages 加
SANPO（CC-BY-4.0），并明确把室内场景列为失败情形，写明"不适合安全关键应用"。Sailens 经过 PC
实验选了 **Depth Anything V2 Small**（Apache-2.0；更大的几个版本是 CC-BY-NC），见 §5。

## 3. 原则

1. **Kotlin 负责含义、状态和安全；C++ 负责昂贵的计算。** 一个计算核要改成 native，必须有
   profiling 证据、正确性基准和绑定覆盖（architecture §6.10）。
2. **VLM 永远不在安全路径上。** Describe 失败不能让 STOP 或障碍物告警消失。
3. **学出来的深度是测量，不是真值。** 它可以说"这里是地面""那里有东西立起来""前面有下沉台
   阶"。障碍物的公制距离来自地平面，不来自深度外推（实测误差见 §5）。
4. **不从缺乏依据的证据推方向**（沿用现有不变量：`suggestedBias` 是质心，不是路线）。M8 之前不
   输出方向。
5. **失效时明确降级。** 输入缺失或过期时，通过非视觉通道降级；绝不能表现得像"前方没东西"。
6. **新行为默认关闭**，只有在仿真器、与冻结基线的 trace 对比、真机运行都给出证据后才打开。
7. **平台保持模型中立。** 深度模型和 `sem`/`det` 一样由用户自带；本仓库不提交权重。没有深度模
   型的 Guidance 是合法配置。
8. **能力边界不变。** 新逻辑作为包放进现有模块；除非出现真正的依赖/API/native 边界，不新增
   Gradle 模块。

## 4. 代码现状（方案依据的事实）

- **障碍物距离不考虑手机俯仰。** `ProcessFrameUseCase` → `DefaultDepthRepository` →
  `ImagePositionDepthEstimator` → `DistanceLevel.fromNormalizedY`，只按框底位置分近/中/远
  （`> 0.75`、`> 0.45`）。手机一抬，近处的人就成了"远"，而 `EventGenerator` 会丢掉远处的非紧急
  障碍物。这是 M3a 首先要修的。
- **没有重力，没有内参。** Guidance 只用加速度计判断"用户是否站着不动"
  （`DeviceMotionDataSource`），代码里没有任何地方读相机内参。
- **安全相关的逻辑分散在多个模块。** `FrameQuality` 在 `sailens-guidance`；`GuidanceStallDetector`、
  `SPEECH_UNAVAILABLE`/`INTERRUPTED`/`VISION_UNRELIABLE` 震动和失效告警在 `sailens-shell`。
  `sailens-guidance` 不能知道输出通道是否健康，`sailens-output` 不能知道 Guidance，所以统一的安全
  状态必须分层（M1）。
- **trace 只记指标。** 帧 trace 记录耗时、标志位和 `messageKeys`（冷却后的候选），不记画面、传
  感器数据，也不记实际送达了什么。今天录下的东西都没法拿来回放新的几何代码。
- **native 绑定覆盖测试有，但只在真机上跑**（androidTest 里的 `Native*BindingCoverageTest`），CI
  不跑。

## 5. 几何方案的依据

PC 实验，2026-09-24，用 `ai-edge-litert` 跑 DIODE 验证集（771 帧，带激光真值深度）和 Cityscapes
路沿样本。数字为"地面可见"帧上的中位数。

| | DA V2 Small | PG depth |
|---|---|---|
| 真实地面在模型视差里是否平面（中位相对残差，室外 / 室内） | **0.5% / 3.8%** | 1.8% / 5.1% |
| 重力 + 正确高度下的地面深度误差（室外 / 室内） | **0.9% / 2.3%** | 1.8% / 7.3% |
| "高于地面 0.25 m"的判断精度（室外 / 室内） | **1.00 / 0.98** | 1.00 / 0.72 |
| 路沿：人行道判为高于车道的比例；估计高度（真实约 10–15 cm） | **93–100%；7–22 cm** | 路面平面拟合只覆盖 22–60% 的路面 |

影响方案的发现：

- **只用相对视差不够**：任何平面在视差里都是线性的，分不清地面和墙；在没有地面的帧上仍会把底
  部约 50% 标成地面。**必须有重力**；加上重力后误报降到约 20%。
- **高度误差线性传导**（高度差 ±15% → 距离差 ±15%）；IMU 偏 2° 误差多 4–5 个百分点，偏 5° 多约
  10 个百分点。
- **用深度外推的障碍物距离不可靠**（室外中位误差 40%，而且偏远，是危险方向）。距离必须来自接
  地点。
- 室内用几何分割地面，IoU 只有约 0.33，所以室内仍只是补充。
- 266×350 输入（29 GOPs）的效果接近 518×686（122 GOPs）。

## 6. 没有 VIO 时的运动：如实的上限

PG 按用户实际移动的方向导航，这个方向来自 ARCore 的公制位姿。没有 VIO 的手持安卓手机能给的只有：

- **可靠的**：几秒内的重力方向和旋转（陀螺仪 / game rotation vector）；
- **不可靠的**：平移和速度（加速度二次积分会漂移；计步器要 `ACTIVITY_RECOGNITION` 权限，
  Sailens 当初刻意避开了）；
- **不等价的**：手持时机身朝向 ≠ 行走方向。

所以第一版 `MotionTracker` 只管旋转，平移报告为未知。局部世界模型做旋转补偿，并保持很短的衰减
窗口，而不是假装融合了平移。ARCore 能给公制位姿，但会接管相机（不能和 CameraX 共用；共享相机
只支持 Camera2），还要依赖 Play Services for AR；它是**最后一个**里程碑（M11），作为相机架构
变更来评估。

## 7. 里程碑

每个里程碑写明：目标 → 交付物 → 退出条件。"用户可见"指行为是否改变。

### M0 — 基线与现场采集（与阶段 2 共用）
- **目标**：一次录制同时服务误报标注（阶段 2）、#5 阈值校准、几何标定和仿真/回放回归。
- **交付物**：冻结基线 commit；trace 记录实际**送达**或**撤回**了什么，而不只是候选；仅 debug
  版的**现场采集**（降采样帧 + 重力/旋转/陀螺仪采样 + 相机内参 + trace）及 JVM 读取器；录制手册
  改用这套采集；`docs/guidance-operating-envelope.md`（支持什么、不支持什么）。
- **退出条件**：在目标设备上录的一段数据能通过 JVM 读取器回放，帧、传感器采样和内参时间对齐；
  基线指标算出。
- **用户可见**：否（仅 debug 版）。

### M1 — Guidance 资格与安全状态（契约）
- **目标**："Guidance 还能不能指引"成为一级状态，而不是分散的告警。
- **交付物**：`sailens-guidance` 里的 `GuidanceQualification`（帧新鲜度、感知健康、几何/运动质
  量）；`sailens-shell` 里合成的 `GuidanceSafetyState`（加上卡死检测和输出健康）；现有告警全部映
  射到它上面；trace 字段。
- **退出条件**：每个状态转换都有单测；测试证明 STOP 类状态会压住普通事件；真机运行的告警与基线
  一致。
- **用户可见**：否（告警不变，只是现在由状态解释）。

### M2 — 确定性仿真器
- **目标**：人为合成边界情况（丢帧、闪烁、俯仰、过期帧、阻塞、恢复），确定性地跑真实决策路径。
- **交付物**：`sailens-guidance` 测试里的 JVM 场景框架；第一批场景；以后能驱动 M0 的采集数据。
- **退出条件**：场景在 CI 中运行，并把今天的行为固定为基准输出。
- **用户可见**：否。

### M3a — 接地点距离（不用模型）
- **目标**：用重力 + 内参 + 假设手机高度（默认 1.3 m）算障碍物距离。
- **交付物**：逐帧相机几何（相机坐标下的重力、内参、时间戳对齐）；带不确定度的接地点距离；由米
  数推出 `DistanceLevel`；退回现有估计器时在 trace 里标明来源；手机高度设置项。
- **退出条件**：仿真器的俯仰场景通过；采集回放显示近/中/远在俯仰变化下保持稳定；打开前先评审与
  基线的 trace 对比。
- **用户可见**：打开后是——距离分级会变。先放在开关后面。

### M3b — 基于学习深度的地面几何
- **目标**：不依赖类别地判断地面、高于地面的结构和台阶/落差，室内室外都适用。
- **交付物**：深度 `ModelType`（用户自带，可选）；深度 runner；重力约束的地面拟合；带地面/高于/
  低于掩码和置信度的观测；2–5 Hz 调度；真机耗时预算和 GPU 争用测量（这吸收了待办的 P3 GPU 仲
  裁，因为深度模型就是新的 GPU 使用者）；调试叠加层和 trace。
- **退出条件**：达到真机预算（§8）；同场景下采集回放与 PC 实验一致；sem/det p95 的劣化不超出预算。
- **用户可见**：否。用几何结果改变提示（例如确认有地面时解除 #5 的"认不出地面"门控，或播报台
  阶）是另一个需要证据的独立决定。

### M4 — 局部世界模型 V0/V1
- **目标**：把"这一帧的观测"和"对前方空间的短期判断"分开。
- **交付物**：以自身为中心、重力对齐的地面网格，由 M3 观测、det 接地点和 sem 可通行区构建；旋
  转补偿；新鲜度和衰减；trace 字段。
- **退出条件**：闪烁和丢帧的仿真场景显示模型能正确保持再正确过期；没有格子活过它的衰减期。
- **用户可见**：否。

### M5 — 运动跟踪（只用旋转）
- **目标**：`MotionState` 带朝向、旋转速度、静止标志和如实的跟踪质量。
- **交付物**：接口 + 只用旋转的实现；拿不到姿态时资格下降；关于计步是否值得一道权限弹窗的决策
  记录。
- **用户可见**：否。

### M6 — 占据与可通行宽度
- **目标**：把"能不能从这里过"和"这是什么"分开。
- **交付物**：基于世界模型的滚动占据；走廊可通行宽度；这里最可能出现第一个新 native 计算核（仍
  需 profiling 证据）。
- **前置条件**：在任何东西从几何上使用 connectivity 之前，先定下 native 计算核与 Kotlin 回退在
  透视缩放上的分歧（重构以来一直悬而未决）。
- **用户可见**：否。

### M7 — 规划器与控制信号（仅调试）
- 基于 M6 的短视距规划器；`GuidanceControlSignal`（HOLD / STEER / STOP、置信度、`validUntil`）；
  只在叠加层、trace 和仿真器里可见。

### M8 — 控制验证
- 振荡、左右来回翻转、过期控制、不安全的恢复、失去资格后仍继续；仿真器 + 采集 + 真机。

### M9 — 空间 earcon 实验
- 接着 [`guidance-validation-roadmap.zh-CN.md`](guidance-validation-roadmap.zh-CN.md) C 阶段做，
  以 `GuidanceControlSignal` 为输入之一。默认值由目标用户的证据决定。

### M10 — native 优化
- 投影、鸟瞰栅格化、占据、距离变换、深度对齐——每一项都要 profiling 证据、正确性基准、绑定覆盖
  和真机对比。

### M11 — ARCore 评估（最后）
- 作为相机架构方案：ARCore 作为另一种 `FrameSource` + 位姿来源，它对 `sailens-camera`、Describe
  取图、设备覆盖（包括没有 Play Services 的设备）、隐私声明的影响，以及现场数据里公制位姿是否
  真的优于假设高度模型。

### 建议的发版分组（无截止日期）
- **版本 A**：M0–M3a（资格状态、仿真器、不受俯仰影响的距离）。
- **版本 B**：M3b–M6（地面几何、世界模型、可通行宽度——仍不输出方向）。
- **版本 C**：M7–M9（控制、验证过的 earcon），以目标用户证据为前提。

## 8. 几何工作的真机预算

在 SM8450 和 SM8850 上测：

1. 用 `benchmark_model` 测每个候选分辨率（266×350、392×518）：GPU fp32 对 fp16（模型卡说 GPU
   fp16 输出会出错——用 20 帧和 PC fp32 结果对比），op 级 profiling 证明没有退回 CPU；SM8850 上
   试一次 NPU。
2. 应用内争用：深度按 3 Hz 与 sem + det 同跑；sem/det 的 p95 和丢帧率与基线对比。
3. 持续 15 分钟：温控状态、耗时漂移、耗电。

建议的门槛：深度 p95 ≤ 35 ms（SM8850）/ ≤ 60 ms（SM8450）；sem/det p95 劣化 ≤ 10%；15 分钟内温
控状态不到 SEVERE。

## 9. 与其他进行中工作的关系

| 工作 | 关系 | 顺序 |
|---|---|---|
| P3 性能：sem mask 所有权（mask 池） | 独立 | 现在就做 |
| P3 性能：相机帧池 | 改动 `FrameSource`/`ImageFrameAnalyzer`，正是 M0/M3a 要加逐帧元数据的地方 | 在 M0 采集之**前**合入 |
| 阶段 2+3：基线、录制手册、误报指标 | 就是 M0 的基线部分；录制若不包含 M0 采集，以后还得重录 | 现在冻结基线 + 补 trace 送达字段；**等采集就绪再录** |
| P3 GPU 仲裁 | VLM 接入已推迟；深度模型是下一个 GPU 使用者 | 并入 M3b |
| P3 sem 降采样 | 会改行为 | 按原计划放在基线之后 |
| #5 地面识别阈值校准 | 需要现场数据 | 用 M0 采集的数据；不单独再跑一轮校准 |
| connectivity 透视分歧 | 影响所有从几何上使用 connectivity 的东西 | M6 之前决定 |

## 10. 不做的事

全局导航或地图路线规划；移植 PG 代码、Bazel、MediaPipe 或 Unreal；PG 声音包；只支持 Pixel 的假
设；把策略或安全状态搬进 C++；M11 之前接 ARCore；M8 之前输出方向；提交模型权重。

## 11. 待评审的问题

1. M0 采集存什么帧率和分辨率（建议：5 Hz、长边 640 px、JPEG），以及采集里含人脸是否可接受（数
   据留在设备上，手动导出）。
