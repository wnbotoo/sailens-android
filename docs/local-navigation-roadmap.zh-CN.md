# 局部导航路线图（吸收 Project Guideline）

> 状态：**提案，先评审**。这里的内容都还没有实现。每个里程碑在写代码前先作为方案评审，单独成
> 一组 PR 合入；除非里程碑明确说明，否则不改变现有 Guidance 行为。发版没有截止日期，完成一组
> 相互配套的里程碑就发一版。实现细节见
> [`local-navigation-implementation.zh-CN.md`](local-navigation-implementation.zh-CN.md)。

## 1. 为什么做

现在的 Sailens Guidance 回答的是"这一帧看到了什么，值不值得提示"（`SceneSnapshot` →
`SceneEvent` → 语音/震动）。这很适合"前方有人""镜头被挡""前方不通"，但下面这些问题它答不了：

- 障碍物有多远，而且不受手机俯仰角影响；
- 前方地面平不平，有没有台阶或落差；
- Guidance 此刻还有没有资格给出指引；
- 以后：用户该往哪边走。

Google 的 [Project Guideline](https://github.com/google-research/project-guideline)（下称 PG）
补上了中间这一层：空间表示、运动、控制、显式 STOP。它 2026 年的后继项目
[Running Guide agent](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/running-guide-agent/)
把设备端快速安全路径和较慢的 VLM 路径分开。本路线图把这些思想吸收进 Sailens 自己的架构。
这不是移植：不复制 PG 代码，PG 只是参考，不是模板。

目标用一句话概括：

```
感知 → 地面几何 → 局部世界模型 →（之后）规划 → 控制 → 无障碍输出
             SceneEvent 继续并存，负责"发生了什么"
```

## 2. PG 实际做了什么，依赖什么前提

读自 PG `main`（2026-09）。前提比技术本身更重要，因为 Sailens 大多不具备这些前提。

| PG 做法 | 位置 | 依赖的前提 | Sailens 的态度 |
|---|---|---|---|
| 在逆深度空间用 RANSAC 拟合缩放和偏移，把相对深度对齐到公制，至少 10 个内点 | `depth/depth_align_ransac.cc` | ARCore VIO 特征点的公制深度 | **借数学**，锚点换成地平面（重力 + 手机高度），不用 VIO |
| 把图像点和固定相机高度的虚拟地平面求交 | `util/hit_test_util.cc`，`camera_height_meters`（默认 1 m，注释写着"待标定"） | 手机固定在腰部背带上；位姿来自 ARCore | **借，但加有效性门槛**：障碍物距离的基础（M3a） |
| 点云 → 重力对齐的通行区占据格（4 m × 5 m，1 m 格，高度带为相机 −0.5…+1.2 m） | `environment/occupancy_map.cc`、`obstacle_utils.cc` | 世界坐标下的公制点云 | **借思路**。但它的高度带丢掉了离地约 0.5 m 以下的一切：**PG 根本不检测路沿、台阶、落差**，Sailens 必须补上 |
| 占据格逐帧计算，不跨帧 | `occupancy_map.h` 注释 | — | 先做逐帧。只有平移已知时才做滚动占据（§6） |
| 报"前方有障碍"前做时间滞回（约 30 帧里要 15 帧） | `util/windowed_value_latch.h` | — | Sailens 已有跟踪和冷却；只对新信号复用这个思路 |
| 按 VIO 速度方向导航，低于最小速度才用相机朝向 | `environment/path_planning.cc:53-60` | 公制 6 自由度位姿（ARCore） | 没有 VIO **无法照搬**：手机 IMU 能给可靠的旋转，给不了平移（§6） |
| 丢失跟踪 → 重置 + STOP | `guidance_system.cc` `OnTrackingStateChanged` | — | **借**：失去资格是一种状态，不是一条提示（M1） |
| 低延迟空间音频 | `audio/` | 耳机，固定声音包 | 已在 [`guidance-validation-roadmap.zh-CN.md`](guidance-validation-roadmap.zh-CN.md) C 阶段规划；不移植 PG 声音包和 AAudio |
| Unreal 仿真器 | `unreal/` | — | **借目的，不借工具**：确定性的 JVM 仿真器（M2） |

PG 里不要重蹈的问题：深度对齐失败时点云不刷新，结果是旧点云配新位姿；
`auto obstacle = obstacles.emplace_back()` 做了拷贝，障碍物位置从没被设置（只是因为调用方只用
`empty()` 才没出事）。

模型：PG 的 `depth.tflite` 模型卡写的是 Apache-2.0，训练数据为带 DPT 伪标签的 OpenImages 加
SANPO（CC-BY-4.0），并明确把室内场景列为失败情形，写明"不适合安全关键应用"。Sailens 经过 PC
实验选了 **Depth Anything V2 Small**（Apache-2.0；更大的几个版本是 CC-BY-NC），见 §5。

## 3. 原则

1. **Kotlin 负责含义、状态和安全；C++ 负责昂贵的计算。** 一个计算核要改成 native，必须有
   profiling 证据、正确性基准和绑定覆盖（architecture §6.10）。
2. **VLM 永远不在安全路径上。** Describe 失败不能让 STOP 或障碍物告警消失。
3. **学出来的深度是测量，不是真值。** 它可以说"这里是地面""那里有东西立起来""前面有下沉台
   阶"。障碍物的公制距离来自地平面，不来自深度外推（实测误差见 §5），而且只在接地点有效时才用。
4. **不从缺乏依据的证据推方向**（沿用现有不变量：`suggestedBias` 是质心，不是路线）。正式输出方向
   有单独的硬门槛（§7"正式方向指引门槛"）。
5. **失效时明确降级。** 输入缺失或过期时，通过非视觉通道降级；绝不能表现得像"前方没东西"。
6. **新行为默认关闭**，只有在仿真器、与冻结基线的 trace 对比、真机运行都给出证据后才打开。
7. **新估计只能先升风险，不能先降风险。** 在现场证据证明之前，新估计器只能保持或提高今天的代码会播
   报的内容，不能把它压掉。
8. **过期的"有东西"只是烦人，过期的"没东西"是危险。** 平移未知时跨帧带过来的信息只能保持风险，绝
   不能把格子判成空地。
9. **平台保持模型中立。** 深度模型和 `sem`/`det` 一样由用户自带；本仓库不提交权重。没有深度模
   型的 Guidance 是合法配置。
10. **能力边界不变。** 新逻辑作为包放进现有模块；除非出现真正的依赖/API/native 边界，不新增
    Gradle 模块。

## 4. 代码现状（方案依据的事实）

- **障碍物距离不考虑手机俯仰。** `ProcessFrameUseCase` → `DefaultDepthRepository` →
  `ImagePositionDepthEstimator` → `DistanceLevel.fromNormalizedY`，只按框底位置分近/中/远
  （`> 0.75`、`> 0.45`）。手机一抬，近处的人就成了"远"，而
  `EventGenerator.shouldAnnounceObstacle` 会丢掉远处的非紧急障碍物。
- **没有重力，没有内参。** Guidance 只用加速度计判断"用户是否站着不动"
  （`DeviceMotionDataSource`），代码里没有任何地方读相机内参。
- **安全相关的逻辑分散在多个模块。** `FrameQuality`（`OK` / `OBSTRUCTED` / `TOO_DARK`）在
  `sailens-guidance`，通过 `SENSOR_QUALITY` 事件在 `EventConflictResolver` 里压住同帧事件。
  `GuidanceStallDetector`、`SPEECH_UNAVAILABLE` / `INTERRUPTED` / `VISION_UNRELIABLE` 震动和失效告
  警是 shell 层的系统提示。没有一个统一状态会撤掉已经排队的普通事件。`sailens-guidance` 不能知道输
  出通道是否健康，`sailens-output` 不能知道 Guidance，所以统一的安全状态必须分层（M1）。
- **trace 只记指标。** 帧 trace 记录耗时、标志位和 `messageKeys`（冷却后的候选），不记画面、传
  感器数据，也不记实际送达了什么。
- **native 绑定覆盖测试有，但只在真机上跑**（androidTest 里的 `Native*BindingCoverageTest`），CI
  不跑。

## 5. 几何方案的依据

PC 实验，2026-09-24，数据为 DIODE 验证集（771 帧，带激光真值深度）和 Cityscapes 路沿样本。方法、
模型哈希、命令和原始汇总见 [`experiments/geometry-probe-2026-09.zh-CN.md`](experiments/geometry-probe-2026-09.zh-CN.md)。
数字为"地面可见"帧上的中位数。

| | DA V2 Small | PG depth |
|---|---|---|
| 真实地面在模型视差里是否平面（中位相对残差，室外 / 室内） | **0.5% / 3.8%** | 1.8% / 5.1% |
| 重力 + 正确高度下的地面深度误差（室外 / 室内） | **0.9% / 2.3%** | 1.8% / 7.3% |
| "高于地面 0.25 m"的判断精度（室外 / 室内） | **1.00 / 0.98** | 1.00 / 0.72 |
| 路沿：人行道判为高于车道的比例；估计高度（真实约 10–15 cm） | **93–100%；7–22 cm** | 路面平面拟合只覆盖 22–60% 的路面 |

影响方案的发现：

- **只用相对视差不够**：任何平面在视差里都是线性的，分不清地面和墙；在没有地面的帧上仍会把底
  部约 50% 标成地面。**必须有重力**；加上重力后误报降到约 20%。
- **高度误差线性传导**（高度差 ±15% → 距离差 ±15%）；重力偏 2° 误差多约 5 个百分点，偏 5° 多约
  11 个百分点。所以手机高度是一个需要标定的量，不是常数。
- **用深度外推的障碍物距离不可靠**（室外中位误差 40%，而且偏远，是危险方向）。距离必须来自接地
  点——而被遮挡或被截断的接地点会出现同样的"偏远"错误，所以它需要自己的有效性门槛。
- 室内用几何分割地面，IoU 只有约 0.33，所以室内仍只是补充。
- 266×350 输入（29 GOPs）的效果接近 518×686（122 GOPs）。

## 6. 没有 VIO 时的运动：如实的上限

PG 按用户实际移动的方向导航，这个方向来自 ARCore 的公制位姿。没有 VIO 的手持安卓手机能给的只有：

- **可靠的**：几秒内的重力方向和旋转（陀螺仪 / game rotation vector）；
- **不可靠的**：平移和速度（加速度二次积分会漂移；计步器要 `ACTIVITY_RECOGNITION` 权限，
  Sailens 当初刻意避开了）；
- **不等价的**：手持时机身朝向 ≠ 行走方向。

缺的是两种不同的能力，不能互相替代：

- **移动方向**——用户往哪边走（朝向、置信度、新鲜度）。正式方向指引需要它。
- **公制平移**——两帧之间用户移动了多远（Δx、Δy、不确定度）。任何跨帧的公制融合（滚动空地、滚动占
  据）需要它。

行走方向可靠，不代表位移可靠；反过来也一样。

写进里程碑的推论：

1. **没有经过验证的*公制平移*来源时，移动中不做跨帧的公制融合。** 按 1–1.5 m/s 算，0.7 s 未知平移
   就是 0.7–1 m 的位置误差，而格子只有 0.1 m。世界模型只做逐帧；只有站着不动时才允许时间融合；跨
   帧带过来的风险证据要按最坏情况下走过的距离扩散，并且永远不能把格子判成空地（M4）。
2. **运行时没有移动方向来源就不能正式输出方向。** 规划器只知道手机朝哪、不知道人往哪走时，不能指
   方向。门槛见 §7。
3. ARCore 能给公制位姿（两种能力都有），但会接管相机（不能和 CameraX 共用；共享相机只支持
   Camera2），还要依赖 Play Services for AR。它仍是**最后一个**里程碑（M11）。推论是：除非 M5 先验
   证并实现了别的方向来源，否则正式方向指引要等到 M11 之后。

## 7. 里程碑

每个里程碑写明：目标 → 依赖 → 交付物 → 退出条件。依赖只指向前面的里程碑。

```
M0 ─┬─ M1 ── M1b
    ├─ M2 ───┘
    └─ M3o ── M3a
          └── M3b ── M4 ── M6 ── M7 ── M8 ── M9
          └── M5a ── M5b        （M5b 方向 → 方向指引门槛；M5b 平移 → M4/M6 滚动融合）
    M10 在 M6–M8 稳定之后；M11 最后（两种能力都能提供）
```

### M0 — 基线与现场采集（与阶段 2 共用）
- **依赖**：P3 相机帧池 PR（同一块代码）。
- **目标**：一次录制同时服务误报标注（阶段 2）、#5 阈值校准、几何标定和仿真场景。
- **交付物**：冻结基线 commit；trace 记录实际**送达**或**撤回**了什么，而不只是候选；两种采集语义
  （实施文档 §4）：
  - **现场证据采集**——降帧率、降尺寸的画面（5 Hz、长边 640 px JPEG）+ 重力/旋转/陀螺仪采样 + 内
    参 + trace，用于标注和几何；它**不能**精确回放感知（缩放和 JPEG 会改变模型输入）；
  - **模型回归记录**——逐帧的感知输出（外加只在标记事件前后保存的完整分析分辨率帧），用于精确回放
    决策路径；

  JVM 读取器；录制手册改用这套采集；`docs/guidance-operating-envelope.md`。
- **退出条件**：在目标设备上录的一段数据能通过 JVM 读取器回放，帧、传感器采样和内参时间对齐；每
  台目标设备的相机时间戳来源和帧/传感器对齐误差都实测过；基线指标算出。
- **用户可见**：否（仅 debug 版）。

### M1 — Guidance 资格与安全状态（契约，精确复现现状）
- **依赖**：M0 基线。
- **目标**："Guidance 还能不能指引"成为一级状态，而不是分散的告警。
- **交付物**：`sailens-guidance` 里的 `GuidanceQualification`；`sailens-shell` 里合成的
  `GuidanceSafetyState`（加上卡死检测和输出健康），附明确的映射表（实施文档 §5），把"我说不出来"
  （输出降级）和"我判断不了路"（失去资格）分开；现有告警全部映射到它上面；trace 字段。
- **行为**：不变。M1 精确复现今天的告警和今天的 `SENSOR_QUALITY` 压制；不加撤回队列。
- **退出条件**：每个状态转换都有单测；真机告警时间线与基线一致。

### M1b — 停止压住已排队事件（改变行为）
- **依赖**：M1、M2。
- **目标**：新的不变量——进入停止类状态时，撤回已排队的普通事件，并在带滞回地恢复资格之前挡住新
  事件。
- **退出条件**：停止/恢复的仿真场景；真机运行与基线对比评审。
- **用户可见**：是（停止之后少一些过时提示）。

### M2 — 确定性仿真器
- **依赖**：M0（读取器，供以后用采集数据驱动的场景）；有 M1 状态时也用上。
- **目标**：人为合成边界情况（丢帧、闪烁、俯仰、过期帧、阻塞、恢复），确定性地跑真实决策路径。
- **退出条件**：场景在 CI 中运行，并把今天的行为（包括 M1 的状态时间线）固定为基准输出。

### M3o — 姿态与相机几何（基础）
- **依赖**：M0（时间戳来源已实测）、P3 帧池。
- **目标**：逐帧得到相机坐标下的重力、分析图像像素单位的内参，以及只含旋转的 `MotionState`（朝
  向、偏航速度、静止标志、姿态质量；平移未知）。M3a、M3b、M4 都用它；这里不依赖任何后面的里程碑。
- **用户可见**：否。

### M3a — 接地点距离（不用模型）
- **依赖**：M3o、M2。
- **目标**：用重力 + 内参 + 手机高度算障碍物距离。
- **交付物**：以区间表示的接地点距离；单独的**接地点有效性**检查（框被截断、接地点被别的检测框或
  sem 掩码挡住、接地点靠近地平线、框的几何不合理）——无效的接地点绝不替换今天的估计；**风险保守
  的融合**——实际使用的分级取"今天的分级"和"按区间**下界**算出的新分级"中更近的那个，所以新估计
  器只能升高或保持风险，绝不会把障碍物推到"远"而被 `EventGenerator` 丢掉；手机高度来自用户/设备
  的几何设置（放置方式预设，可选用身高细化），不来自运行参数预设。
- **启用门槛**（代码可以先合入，默认关闭）：已设置放置方式预设或身高换算；仿真俯仰场景通过；采集回放
  和真机证据已与基线对比评审。
- **用户可见**：过了启用门槛才可见。

### M3b — 基于学习深度的地面几何
- **依赖**：M3o、M2。
- **目标**：不依赖类别地判断地面、高于地面的结构和台阶/落差，室内室外都适用。
- **交付物**：深度 `ModelType`（用户自带，可选）；深度 runner；重力约束的地面拟合；带地面/高于/
  低于掩码和置信度的观测，通过明确的**深度输入变换**（实施文档 §9）表达在分析图像坐标系里——模型没
  看到的区域一律是未知，绝不插值；2–5 Hz 调度；真机耗时预算和 GPU 争用测量（吸收待办的 P3 GPU 仲
  裁）；调试叠加层和 trace。
- **失效范围**：深度是可选能力。没有模型或模型失效时，深度几何能力不可用，而 Guidance 的基础资格不
  变——配置了但坏掉的深度模型，绝不比没配深度模型更糟。只有已启用且依赖深度的面向用户的功能才受影
  响（实施文档 §5，按能力划分资格）。
- **退出条件**：达到真机预算（§8）；同场景下采集回放与 PC 实验一致；sem/det p95 的劣化不超出预算。
- **用户可见**：否。用几何结果改变提示（例如确认有地面时解除 #5 的门控，或播报台阶）是另一个需要
  证据的独立决定。

### M4 — 局部世界模型 V0（逐帧）与 V1（静止时 / 只保持风险）
- **依赖**：M3o、M3a、M3b。
- **V0**：以自身为中心、重力对齐的地面网格，每帧只用当前观测重建（M3b 的地面/高于/低于、det 接地
  点、sem 可通行区）。没有跨帧记忆。
- **V1**：只在以下情况做时间融合：(a) `MotionState.isStationary` 时；(b) 对*风险*证据（有东西、落
  差），按 `v_max · 时长` 扩散并很快过期。移动时绝不跨帧保留空地。
- **退出条件**：闪烁/丢帧的仿真场景；一个用户在走的场景证明没有格子因为过去的观测被判成空地。
- **用户可见**：否。

### M5a — 移动来源：评估
- **依赖**：M3o、M0 采集数据。
- **目标**：在 M0 采集数据上离线评估不靠 ARCore 的候选方案——基于计步的航位推算（需要先定权限），以
  及从相邻帧估计的视觉运动（例如借助 M3 地平面的地面光流）。刚性固定暂不验证（2026-09-25 决定）。
- **产出**：决策记录，给出**两个独立结论**，各自为"已验证 / 未验证"并附证据：*移动方向*
  （`MovementDirectionEstimate`）和*公制平移*（`TranslationEstimate`）。
- **用户可见**：否。

### M5b — 移动来源：运行时实现
- **依赖**：M5a（只针对结论为"已验证"的那一项）。
- **目标**：在 `MovementDirectionSource` / `TranslationSource` 接口后实现选定的来源，带新鲜度、置信度
  和失败上报，并在真机上对照 M5a 的证据验证。
- **退出条件**：每个实现的能力都通过真机验证；记入 trace。
- **用户可见**：否。

### M6 — 占据与可通行宽度
- **依赖**：M4；带平移补偿的滚动占据还需要运行时有经过验证的**公制平移**来源（M5b 的平移或 M11）——
  只有方向来源不够。否则只做逐帧 / 静止时。
- **前置条件**：在任何东西从几何上使用 connectivity 之前，先定下 native 计算核与 Kotlin 回退在透
  视缩放上的分歧。
- 这里最可能出现第一个新 native 计算核（仍需 profiling 证据）。

### M7 — 规划器与控制信号（仅调试）
- **依赖**：M6。短视距规划器；`GuidanceControlSignal`（HOLD / STEER / STOP、置信度、
  `validUntil`）；只在叠加层、trace 和仿真器里可见。

### M8 — 控制验证
- **依赖**：M7。振荡、左右来回翻转、过期控制、不安全的恢复、失去资格后仍继续；仿真器 + 采集 + 真机。

### M9 — 空间 earcon 实验
- **依赖**：M8。作为实验接着 [`guidance-validation-roadmap.zh-CN.md`](guidance-validation-roadmap.zh-CN.md)
  C 阶段做，以 `GuidanceControlSignal` 为输入之一。

### 正式方向指引门槛（不是里程碑，是条件）
`GuidanceControlSignal.STEER` 只有在以下**全部**成立时才对用户输出：M8 通过；M9 有目标用户证据；并
且**要么**有已在运行时实现、并通过真机验证的移动方向来源（M5b 或 M11），**要么**运行条件要求刚性固
定、且其前向轴就是行走方向，并经过现场验证（目前不计划）。只有离线决策记录不满足这个门槛。否则 STEER
只用于调试。停止类的安全行为（M1b）可以更早上线；它不是控制信号。

### M10 — native 优化
- 在 M6–M8 稳定之后。投影、鸟瞰栅格化、占据、距离变换、深度对齐——每一项都要 profiling 证据、正确性
  基准、绑定覆盖和真机对比。

### M11 — ARCore 评估（最后）
- 作为相机架构方案：ARCore 作为另一种 `FrameSource` + 位姿来源，它对 `sailens-camera`、Describe
  取图、设备覆盖（包括没有 Play Services 的设备）、隐私声明的影响，以及现场数据里公制位姿是否真的
  优于标定高度模型。

### 建议的发版分组（无截止日期）
- **版本 A**：M0、M1、M2、M3o、M3a 代码（M3a 默认关闭，除非过了启用门槛），M1b 就绪也可以带上。
- **版本 B**：M3b、M4、M6（逐帧 / 静止时）、M5a 的决策（有"已验证"的结论时再做 M5b）——仍不输出方向。
- **版本 C**：M7–M9 作为实验。正式方向指引只能通过它的门槛。

## 8. 几何工作的真机预算（待测）

计划在 SM8450 和 SM8850 上测：

1. 用 `benchmark_model` 测每个候选分辨率（266×350、392×518）：GPU fp32 对 fp16（模型卡说 GPU
   fp16 输出会出错——用 20 帧和 PC fp32 结果对比），op 级 profiling 证明没有退回 CPU；SM8850 上
   试一次 NPU。
2. 应用内争用：深度按 3 Hz 与 sem + det 同跑；sem/det 的 p95 和丢帧率与基线对比。
3. 持续 15 分钟：温控状态、耗时漂移、耗电。

建议的门槛：深度 p95 ≤ 35 ms（SM8850）/ ≤ 60 ms（SM8450）；sem/det p95 劣化 ≤ 10%；15 分钟内温
控状态不到 SEVERE。

## 10. 不做的事

全局导航或地图路线规划；移植 PG 代码、Bazel、MediaPipe 或 Unreal；PG 声音包；只支持 Pixel 的假
设；把策略或安全状态搬进 C++；M11 之前接 ARCore；绕过门槛正式输出方向；提交模型权重。

## 11. 评审后的决定与剩余问题

已采纳（PR #7 评审）：

- M0 采集按 5 Hz / 640 px JPEG 作为现场证据，不作精确回放；精确回放用记录下来的感知输出加事件窗口
  内的完整帧。
- 手机高度：1.3 m 只是初始值；启用 M3a 需要校准（形式见下方决定：放置方式预设，可选用身高细化）。
- M3a 代码可以随版本 A 合入，但在过启用门槛之前默认关闭。
- 版本 A 的运行条件声明不支持：跑步、楼梯/落差指引、过马路指引、方向指引，以及 M3a 没有验证过的任
  何手机放置方式。

之后决定（2026-09-25）：

- **校准 = 放置方式预设**（胸前挂绳 / 手持齐胸 / 腰部），每种带默认高度。可选的低成本细化：用户填写身
  高，按预设比例换算手机高度。不做引导式距离校准——它要求盲人用户知道自己离墙多远，而这正是我们要测
  的东西。
- **采集可以包含人脸。** 保留：录制后 7 天自动删除，已导出或在调试 UI 里标记保留的除外；总量上限 2 GB，
  超出先删最旧的。
- **暂不验证刚性固定。** M5a 只评估计步和视觉运动两种来源；因此正式方向指引要等某个方向来源在 M5a 验
  证、并在 M5b 实现，或者等 M11。
