# 提示系统真机验证与空间化 Earcon 路线图

> 状态：**延期规划**。当前缺少设备、测试人员与现场采样资源，本文件不代表这些能力已通过验证，也不能作为发布证据。

## 目标

在继续扩展提示系统前，用真机证明以下安全属性：

1. 风险升级不会被冷却压住；重复或抖动事件不会刷屏。
2. TalkBack、本应用 TTS 与震动不会重复、互相抢占或同时失效而保持静默。
3. 实时状态只展示仍有效的风险；重播历史不会伪装成当前风险。
4. 中断、TTS 失效和镜头失效都能通过至少一条非视觉通道被察觉。
5. 空间化 earcon 只有在目标耳机上被可靠识别后，才进入正式导航链路。

## 启动条件

至少准备：

- 2 台不同厂商的 Android 真机，覆盖不同振动马达与 TTS 实现；
- 1 副目标用户常用的骨传导耳机，以及 1 副普通立体声耳机作为对照；
- TalkBack、至少 2 个可用 TTS 引擎；
- 可同时播放的播客或导航音频；
- 能导出 Sailens JSONL log、trace、录屏和外部录音的测试环境；
- 至少 1 名不参与提示设计的测试者；涉及目标用户结论时，应由盲人或低视力用户参与。

所有通过标准先作为工程门槛；真正的可用性结论必须由目标用户测试确认。

## Phase A：现有提示链路真机验收

### A1. TalkBack 通道互斥

场景：运行中开启/关闭 TalkBack，连续触发不同优先级事件并执行重播。

验收：

- 每个事件只听到一次，不出现 TalkBack 与应用 TTS 重复朗读；
- TalkBack 接管时应用 TTS 停止并归还音频焦点；
- 关闭 TalkBack 后应用 TTS 能恢复；
- 重播走当前有效的语音通道。

### A2. 冷却与风险升级

场景：同一 cooldown key 依次产生 HIGH、CRITICAL、HIGH、CRITICAL，并覆盖 0–800ms 内升级。

验收：

- 第一次 CRITICAL 立即放行，没有人为增加的 800ms 静音窗口；
- 后续降级不会绕过冷却；
- CRITICAL 不因类别来回抖动而逐帧重复；
- trace 中的生成、过滤和实际输出顺序一致。

### A3. TTS 失效

场景：禁用或破坏当前 TTS 引擎，使状态从 INITIALIZING/READY 进入 UNAVAILABLE。

验收：

- 每次进入 UNAVAILABLE 只播放一次 `SPEECH_UNAVAILABLE` 震动；
- 状态持续为 UNAVAILABLE 时不重复震动；
- TalkBack 已接管或语音关闭时不产生无关告警；
- 用户能够把该节奏与 `SENSOR_FAILURE`、`INTERRUPTED` 区分开。

### A4. 实时状态与重播

场景：触发事件，随后进入冷却空帧，等待事件过期，再执行重播。

验收：

- 空帧不会让状态卡片立即闪回“无风险”；
- `expiresAt` 后实时卡片清除旧风险；
- 旧提示仍可按用户意图重播，但明确不表示风险仍存在；
- 停止会话后实时状态与重播历史都清空。

### A5. 生命周期中断

分别测试息屏、来电、Home/最近任务、权限撤销和进程被系统回收。

验收：

- 辅助意外停止时，震动先于或独立于语音到达；
- 中断只告警一次，不因 Activity 重建或旋转误报；
- UI 不继续呈现“正在保护”的假状态；
- 若产品未来承诺后台/息屏导航，再按[后台导航规划](background-guidance-plan.zh-CN.md)完成前台服务验收。

### A6. 音频协调

场景：同时播放播客、地图导航和 TalkBack，连续触发普通、高优先级及重播提示。

验收：

- 语音提示可听懂，不被其他音频覆盖；
- 音频 ducking 不持续、不来回抽动；
- 提示结束或被新提示打断后正确归还焦点；
- 不出现新 utterance 播放中却因旧回调提前归还焦点的情况。

## Phase B：震动词汇盲测

测试者不知道当前播放的符号，在手持、衣袋和步行三种状态下区分：

- 导航障碍；
- `SPEECH_UNAVAILABLE`；
- `SENSOR_FAILURE`；
- `INTERRUPTED`。

记录每种符号的混淆矩阵、漏感知率、识别时间和设备型号。暂定工程门槛：整体正确率至少 90%，三种失效告警之间不得出现系统性混淆。未达标时先调整节奏，不用 UI 文案补偿不可辨识的震动。

## Phase C：空间化 Earcon 实验

Earcon 首先是独立实验页，不接入正式事件决策，也不默认开启。

### C0. 左右定位最小原型

- 只使用一种短音色和 LEFT/RIGHT 两个位置；
- 用 `AudioTrack` 运行时合成立体声 PCM，控制包络和左右声道；
- earcon 不申请音频焦点；
- 仅耳机接入时提供方向，外放自动回落到语音；
- 记录事件产生到声音起播的 p50/p95 延迟。

进入下一阶段的暂定门槛：骨传导耳机上的左右盲测正确率至少 90%，街道噪声下仍能察觉，且 p95 起播延迟不超过 250ms。达不到时只保留无方向提示，不用更强声像或更大音量掩盖问题。

### C1. 距离与类别

只有 C0 通过后，才依次验证：

1. 距离使用重复频率表达，禁止用音量表达；
2. 人、车、静态障碍三种音色的混淆矩阵；
3. CRITICAL/HIGH 使用 earcon 后接短语音；
4. MEDIUM/LOW 是否允许仅 earcon，必须由目标用户测试决定，不能仅凭打扰量推断。

### C2. 降级与设置

- 设置提供仅语音、仅 earcon、两者三种模式；默认值在目标用户测试后决定；
- 提供可重复试听的校准页；
- 耳机断开、单声道输出或声道分离不足时自动回落到语音；
- trace 记录输出模式、音频路由、earcon 参数、请求时间和实际起播时间。

## 每次测试必须保留的证据

- 设备、Android 版本、耳机、TTS 引擎和 TalkBack 版本；
- Sailens commit SHA、runtime profile 与设置快照；
- 对应 log、trace、录屏/录音；
- 每个场景的预期结果、实际结果和时间戳；
- 失败是否可重复、是否仅发生于特定设备；
- 震动/earcon 盲测的原始试次与混淆矩阵，而不只保留汇总百分比。

## 完成定义

只有 Phase A 全部通过，当前提示系统才能从 **Conditional Go** 转为设备层面的 **Go**。Phase B 或 C 未通过不阻止纯语音/震动版本发布，但对应词汇或 earcon 功能必须保持关闭。任何门槛调整都应基于保存下来的设备证据，不以放宽阈值代替能力建设。
