## 1. PR-1a：撤回机制（D3a-1，不改语义）

### 1.1 今天的实现和它的缺陷

`DecideEventsUseCase` 每帧只为排第一的那条事件记冷却（暂记），送达方没送出去就调 `RevokeUndeliveredEventUseCase` 撤回。
`CooldownManager` 的撤回是**快照式**的：`recordEvent` 记下这次写入之前每个 key 的旧记录，`revoke` 把"仍由这条事件写着"的
key 恢复成旧记录，并从风暴计数里删掉一个同时间戳的条目。

记录规则（`recordEvent`）：同一个 key 上，新写入在上一条记录的基础冷却内、而上一条的优先级更高时，继承上一条的优先级。所以
最高优先级沿连续写入一直继承。

快照式撤回只在"撤回的是最后一次写入、并且在下一次写入之前"时正确。反例（交错撤回）：

| 步骤 | 今天的 key `K` |
|---|---|
| t = 0 写入 A（CRITICAL） | A，CRITICAL |
| t = 1 写入 B（HIGH，在窗口内，继承） | B，CRITICAL（继承自 A） |
| 撤回 A | 不变：`K` 已由 B 写着；B 的记录仍带着从 A 继承的 CRITICAL |
| 撤回 B | 恢复成 B 写入之前的旧记录 = **A，CRITICAL** |

A 和 B 都没送达，`K` 上却留着 A 的 CRITICAL 记录，一个冷却周期内同级和更低的提示都会被它挡住。方案 §1.4 的统计里，7 段旧录制
的 670 次撤回都落在"自己那次决策之后、下一次决策之前"，所以至今没触发；但这个顺序不是代码保证的（流水线和收集者之间有缓冲）。

### 1.2 新的状态结构

一次 `recordEvent` 叫一次**写入**：事件 id、时间、优先级，以及它写的每个 key 和该 key 的基础冷却（按写入事件的类别和 key 取，
和今天 `baseCooldownFor` 一样）。冷却管理器保存：

- **已确认前缀的摘要**：所有已确认写入按今天的规则依次折叠后的每 key 记录（时间、继承后的优先级、写入者）。它是完整折叠的
  结果，不是按窗口裁剪后重放——继承链可以任意长（中心窗口 4 s：t = 0 CRITICAL、t = 3 HIGH、t = 6 HIGH，t = 6 的记录仍是
  CRITICAL）。
- **未并入摘要的写入**：按写入顺序的列表。每条要么待定，要么已确认但排在某条待定写入之后。
- **当前记录** = 把未并入的写入按顺序折叠到摘要上。缓存起来，撤回时重算；`filter` 和 `snapshot` 只读它。

折叠规则就是今天 `recordEvent` 的那几行，一字不改（新记录的时间 = 写入时间；在旧记录的基础冷却内且旧记录优先级更高时继承
旧优先级，否则用写入的优先级；写入者 = 这次写入）。

### 1.3 确认、撤回与上限

- **确认 `confirm(id)`**：把这次写入标为已确认，然后推进摘要：只要列表最前面的写入已确认，就把它折进摘要、移出列表。**摘要只
  推进连续的已确认前缀**：B 先确认、A 还待定时，B 留在列表里，等 A 有了结果再一起推进。确认不改变当前记录（折叠是顺序的，
  把列表头折进摘要不改变整体结果），只决定之后还能不能撤回。
- **撤回 `revoke(id)`**：写入仍在列表里且待定 → 删掉它，重新折叠当前记录，再推进摘要。已确认、已并入摘要或未知的 id → 空操作。
  返回值（撤回生效时已完成的决策次数，M0b 用）不变。
- **上限**：未并入的写入超过 16 条时，最旧的一条被强制确认并折进摘要。这对应今天 `undoLog` 只保留最近 16 条、更旧的撤回是空
  操作。因为未并入的写入总是"全部未撤回写入"的一个后缀，它的条数不会多于今天的 `undoLog`，所以上限不会比今天更早生效。
- **一直没有结果的写入**（决策后送达方没给结果，例如会话停止）：和今天一样一直算数，直到被上限挤出或 `reset()`。PR-1a 不改
  这一点。

### 1.4 风暴计数

`recentEmissions` 的每个条目带上写入者 id。确认部分和可撤回部分的区别由写入列表决定：撤回只在写入仍待定时进行，并且只删
**自己那条**（按 id，而不是按时间戳找最后一条）。滑窗裁剪（`trimEmissionWindow`）不变。

### 1.5 确认时机（保持今天的接收语义）

确认 = 送达方说"至少一个通道接收了"，也就是 `deliverGuidanceEvent` 返回的通道非空。逐通道：

| 通道 | 何时确认 |
|---|---|
| 自带 TTS | `speak` 返回接收 |
| TalkBack | 已发布给读屏（`announce` 之后） |
| 只有震动 | 马达仲裁接收（`HapticManager.trigger` 返回 true） |
| 语音和震动都关 | 状态卡 |

没送出去的两条路径照旧撤回：等描述（`WAITING_FOR_DESCRIPTION`）、没有通道接收（`OUTPUT_REFUSED`）。新增
`ConfirmDeliveredEventUseCase`，与 `RevokeUndeliveredEventUseCase` 并列；`offerGuidancePrompt` 在送达时调它。
等完整说完才确认属于 PR-1b（D3b-4），不在这里。

### 1.6 回放与录制：不记录确认

M0b 录制只记撤回的位置，PR-1a 不加"确认"记录、不改 schema。理由：

- 当前记录 = 摘要上顺序折叠全部**未撤回**写入，与哪些写入已确认无关；确认只影响之后的撤回能不能生效。
- 生产中一条事件要么确认、要么撤回，不会两者都有。回放从不确认，于是回放的未并入写入 = 最近 16 条未撤回写入；设备上的未并入
  写入是它的一个后缀，而且必定包含所有待定写入。所以设备上生效的撤回在回放里也生效，设备上因上限而失效的撤回在回放里也失效。
- 结论：只按录下的撤回位置回放，结果与设备逐位相同。这条有 JVM 测试（"设备"确认 + 撤回 vs "回放"只撤回，随机序列）。

### 1.7 等价性声明

**条件**：初始状态相同，并且每次撤回的都是当前最后一条仍可撤回的写入、而且在下一次写入之前撤回（7 段旧录制的 670 次撤回全部
满足；C 组见第 4 节）。**在这个条件下，新旧两个实现的全部 key 的记录（时间、优先级、写入者）和风暴计数逐位相同**，`filter`、
`snapshot`、`revoke` 的返回值也相同。

证据分三层：

1. **性质测试**：新实现与今天实现的逐字副本（测试源集里的 `LegacyCooldownManager`）在满足条件的随机写入/撤回/静止切换/空决策
   序列上逐步比较全部 key 的记录、风暴计数和过滤结果。
2. **有意修掉的缺陷**：不满足条件的序列上新实现不再留下未送达的记录。必须有的用例：A→B 写入后先撤 A 再撤 B（第 1.1 节的表）；
   确认 B 后撤回 A（B 的记录用它自己的优先级，之后撤回 B 是空操作）；撤回顺序反过来；合并事件的多组 key。
3. **回归证据**：C 组 14 段的精确回放和 `PromptPolicyBaselineTest` 报告逐行不变（第 4 节）。这不当作等价性证明。

### 1.8 不改的东西

决策、冷却规则和窗口、语音和震动仲裁、`SceneEvent`、M0b schema 和比较规则、精确回放、全部现有基准。shell 只多了一次
`confirm` 调用。

## 2. PR-D5：功能降级告知（D5）

### 2.1 要补的缺口

镜头遮挡（OBSTRUCTED，CRITICAL）、过暗（TOO_DARK，HIGH）、地面认不出（GROUND_UNRECOGNIZED，LOW）今天是普通导航事件，走
`deliverGuidanceEvent`：

- 语音被同级或更高的播报拒绝时不震动；震动受"震动提醒"开关控制。
- 每帧只送排第一的事件。地面认不出是 LOW：只要一直有障碍物提示，它就一直排不上，用户可能一次都听不到。
- 下一帧重新给出只保证**重试**，不保证在多长时间内送达。

### 2.2 结构

- **Guidance 不变**：三种事件照常生成、照常冷却、照常记进 M0b。新增的只是把"这一帧哪些状态在生效"交给 shell：
  `SceneResult.visionFaults`（帧质量的去抖结果、地面是否已确认认不出），由 `EventGenerator.visionFaults(snapshot)` 给出——
  它和 `generate` 用同一个判断（含 `enableSensorQualityEvents` 开关），所以"D5 告警的状态"和"Guidance 生成状态事件的状态"
  是同一件事。决策输出逐位不变。
- **shell 新增 `VisionFaultAlerts`**（纯逻辑，JVM 可测，和 `GuidanceStallDetector`、`SpeechUnavailableAlert` 同类），负责这三种
  状态的**全部**语音和震动：进入、重复、补偿、兜底、恢复。它每帧在送完这一帧的导航提示之后更新（先送导航提示：否则同一帧里
  后到的更高优先级提示会把刚开口的地面告知冲掉）。
- **这三类事件做主事件时**，shell 不再自己播，而是确认它的冷却记录，并记一条 `prompt_outcome`，通道是新增的
  `vision_alerts`。冷却照常节流这条事件（状态卡、重播、trace 的节奏和今天一样）；用户有没有听到由 `VisionFaultAlerts` 自己跟踪。
  不这样做的话，进入时会说两遍（事件一遍、告警一遍）。

### 2.3 状态与滞回

两条轨道：

- **帧质量轨道**：OK / OBSTRUCTED / TOO_DARK，输入是 `FrameQualityAnalyzer` 去抖后的结果（连续 6 帧一致才切换，今天的去抖）。
  在它之上加一个**恢复保持** H = 2 s：变回 OK 后要持续 2 s 才算恢复。保持期间不出新周期、不兜底；保持期内又遮挡上，就当作没恢复
  过（不再震进入震动、不重说），周期接着算。手在镜头前晃动时不会"遮挡/恢复/遮挡"地刷屏。
  OBSTRUCTED 和 TOO_DARK 之间直接切换：开始新状态的周期（说新状态的告知），不震进入震动，也不说恢复。
- **地面轨道**：RECOGNIZED / UNRECOGNIZED，输入是 `GroundRecognitionAnalyzer` 已确认的结果（进入要持续
  `groundUnrecognizedEnterMs`，退出要持续 `groundUnrecognizedExitMs`，今天的确认时长），不再另加保持。
  **帧质量有故障（含保持期）时地面轨道冻结**：画面不可信时地面判断也不可信；这和 `EventConflictResolver` 让 SENSOR_QUALITY 压掉
  其余事件一致。帧质量恢复后地面轨道按当时的输入继续：仍认不出就开始地面的进入告知；之前已告知认不出、现在认得出就说地面恢复。

### 2.4 每种状态的告知和节奏

| 状态 | 告知优先级 | 文案（进入） | 周期 P | 期限 D | 进入震动 | 每周期震动 | 恢复提示 |
|---|---|---|---|---|---|---|---|
| OBSTRUCTED | CRITICAL | `event_camera_blocked` | 8 s | 5 s | 是 | 是 | `event_camera_restored` |
| TOO_DARK | HIGH | `event_low_light` | 15 s | 6 s | 是 | 否 | `event_light_restored` |
| GROUND_UNRECOGNIZED | LOW | `event_ground_unrecognized` | 60 s | 10 s | 是 | 否 | `event_ground_recognized` |

- 周期和优先级都是今天的值（今天的 key / 类别冷却：8 s、15 s、60 s；事件优先级：CRITICAL、HIGH、LOW），只是从冷却挪到了
  `VisionFaultAlerts`。
- 震动都是 `VISION_UNRELIABLE`（长-短-长），强度不低于 HIGH 档（遮挡用 CRITICAL 档），和今天 `amplitudeFor(event)` 一样。
- 期限 D 的来历：D1.7 时长表在语速 1.30 下，三句中文是 1.18 / 1.06 / 3.41 s，英文 1.03 / 1.01 / 2.95 s；最慢语速 0.7 下约放大
  1.86 倍（2.2 / 2.0 / 6.3 s）。D 要能容下"前面一句正在说的提示 + 这一句"。语速 1.30 下三个 D 都留了一倍以上的余量；在最慢语速下
  遮挡可能来不及，后果是一次多余的兜底震动（见 2.6，不会重说）。这三个数没有真机校准，代码里标注。
- 每个周期要的是**一次完整说完的告知**。下一周期从上一周期开始的时刻加 P 算起。

### 2.5 语音告知怎么说

- **路径**：`SpeechManager.speak(Announcement)`，也就是导航提示自己的路径（QUEUE_FLUSH）。接收就意味着立刻开口：**它前面没有
  任何排队的话**（0 条）。不用 `speakSystemNotice`：那条路径是 QUEUE_ADD，排在整个队列后面，保护期从请求时开始算、包含排队时间
  （方案 D5-1）。
- **仲裁**：和导航提示同一个规则——只有严格更高的优先级能打断。告知优先级见 2.4。遮挡和过暗时 Guidance 本来就不出其它提示
  （冲突消解只留 SENSOR_QUALITY），能挡住它们的只有之前那句还没说完的导航提示和"辅助中断 / 出错停止"这类最高级通知；地面告知
  是 LOW，任何 MEDIUM 以上的导航提示都能冲掉它——这时靠补偿和兜底（2.6）。
- **保护期限**：每次尝试的 `expiresAtMs` = 尝试时刻 + D。过期前它在喇叭仲裁里算"正在说"，挡住同级和更低的话；丢了完成回调
  也最多挡 D。
- **描述**：和导航提示同一条规则（`guidanceWaitsForDescription`）。遮挡、过暗（≥ HIGH）先打断描述再说；地面（LOW）等描述说完，
  期限照常计时，等过了期限就兜底震动。
- **重试**：被拒绝（同级或更高在说、引擎未就绪、在等描述）就在之后的帧上再给，最快每 500 ms 一次（拒绝也会在 PR-0 的生命周期
  录制里留一条记录，不能每帧刷）。**被接收之后，期限之前不再给**：它可能还在说，再给只会被自己挡住（同级不能打断）或者重说一遍。
  期限到了还没说完，重发一次。所以**每个周期最多 2 次被接收的尝试**（第一次 + 期限后的一次重发）：被冲掉的告知还有一次机会，但
  不会在商场里一遍遍说半句。同一状态任何时候最多只有一条正在说的告知。
- **读屏（TalkBack）**：语音开、读屏开时发布给读屏，发布即算说完（读屏没有完成回调，这和 PR-1a 的接收语义一致）。见 2.11。
- **语音关**：不说，见 2.7。

### 2.6 完整说完的判定、补偿与兜底

- **完整说完** = 引擎对这条告知的某一次提交报了 `onDone`（Android 契约：可听输出已播放完毕），和 D1.3-3 的完成规则相同：被
  `withdraw` 交还后换了新的提交 id 也算同一条，`onDone` 晚于 FLUSH 也算。
- **实现**：`SpeechManager.speak` 新增可选参数 `onSpoken`，在主线程上、某次提交收到 `onDone` 时调一次（按逻辑 id 匹配：交还的
  提交 id 是原 id 加后缀）。只给要知道结果的调用方用；最多同时登记 16 个，旧的挤掉。**不复用 PR-0 的生命周期观测通道**：那条通道
  只在 debug 录制时挂观测者、是单一槽位、带会话对账，PR-0 也承诺过"没有任何决策读它"；生产决策不能依赖 debug 录制是否开着。
  两者用同一份引擎证据（`onDone`），口径一致。
- **补偿**：期限 D 到了这一周期的告知还没说完——不管原因（被丢弃、被冲掉、过期、没有完成回调、引擎未就绪、在等描述）——就：
  1. **兜底震动一次，不看任何开关**（导航提示震动、故障告警震动都不看）；
  2. 重发一次（第一次一直没被接收的，就继续每 500 ms 给一次，直到被接收；每周期最多 2 次被接收的尝试）。
  之后每个周期照样：期限到了没说完就再兜底一次。所以"语音告知说不出来"时，兜底震动按该状态的周期（8 / 15 / 60 s）持续，直到
  告知说完或状态恢复。引擎一直 READY、告知反复被冲掉或一直没有完成回调，同样走这条路。
- **一次多余的兜底**：慢语速或回调晚到时，兜底可能在告知还在说的时候震；同级告知不能打断自己，所以不会重说，代价只是一次震动。

### 2.7 震动设置

"震动提醒"拆成两项：

| 设置 | 默认 | 管什么 |
|---|---|---|
| 导航提示震动（今天的开关，改名） | 开 | 障碍物方位、前方不通、路况提示等导航提示的震动 |
| 故障告警震动（新） | 开 | 遮挡、过暗、地面认不出的进入震动，以及遮挡的每周期震动 |

始终不看开关的：兜底震动（2.6）、语音失效（`SPEECH_UNAVAILABLE`）、辅助中断和出错停止（`INTERRUPTED`，Q11b：保持完全不可关）。

**语音关时故障告警震动锁定为开**（Q11a）：设置页显示为开、不能切换，并写明原因（"语音提醒已关闭，镜头被挡、太暗、认不出地面时
只能靠震动告诉你"）。实现上生效值 = 故障告警震动 ∨ 语音关；存储里用户自己的选择保留，语音重新打开后恢复。

语音关时告知没法说出口，每个周期的那一下就是震动本身：遮挡每 8 s、过暗每 15 s、地面每 60 s 震一次，直到恢复。这就是方案 D5-3
"之后按该状态的重复节奏继续兜底"在语音关时的样子，不另算兜底，不会同一周期震两下。

### 2.8 恢复提示

- 三条新文案，进 `SceneEventMessageKeys`（Guidance 词表）和 `SceneEventStrings`（shell 映射），`values/` 和 `values-zh/` 都有：
  - `event_camera_restored`：镜头恢复正常 / Camera is clear again
  - `event_light_restored`：光线恢复正常 / Light is back to normal
  - `event_ground_recognized`：已识别到地面，恢复通行判断 / Ground recognized again, path alerts are back
- 优先级 LOW，尽力而为：恢复后 5 s 内被接收就算说过，过了 5 s 还没说出来就放弃；不跟踪完成、不补偿、不震动（说漏了"已恢复"，
  用户以为还没恢复，是安全的一侧）。
- 只在真正恢复时说：帧质量要回到 OK 并保持 2 s；OBSTRUCTED↔TOO_DARK 互换不说恢复。同一帧里镜头和地面可以先后恢复，所以没说出来的
  恢复提示排成队、按先后说（每帧最多给一条）。作废规则：帧质量再出故障时全部作废（画面不可信，"已识别到地面"也不成立了）；地面
  再认不出时只作废地面自己的恢复提示（镜头确实恢复了）。
- 语音关时没有恢复提示（只靠周期震动的停止）。这是已知局限（2.11）。

### 2.9 与其它告警的关系

- `SPEECH_UNAVAILABLE`（语音引擎彻底失效）照旧：一次专属震动，不看开关。D5 的告知在引擎未就绪时被拒，期限一到兜底震动；两种
  震动节奏不同（短-短-特长 vs 长-短-长），分别说"说不出话"和"看不清"。
- `STALLED` / `FAILED` / `INTERRUPTED` 照旧。没有新帧时 `VisionFaultAlerts` 不更新（它只由帧驱动），失效由卡顿检测负责。
- 停止导航：`VisionFaultAlerts` 复位，不说恢复。

### 2.10 Guidance 词表和 trace

- `SceneEventMessageKeys` 加三个恢复 key（`all` 随之扩大，`SceneEventStringsTest` 守住映射）。`scripts/verify-release-strings.py`
  只认 `event_` 开头的资源名，三个新名字都符合。
- `PromptDeliveryChannels` 加 `vision_alerts`。旧读取器读到新 trace 会拒绝这个未知通道——本仓库内读写同时更新。
- M0b schema 不变。D5 的告知在 PR-0 的生命周期录制里以逻辑 id `vision_notice_<n>` 出现，和系统通知一样是"非导航提示的语音"；
  将来的评估要把它们当作占喇叭的其它语音（PR-1b 详细设计里交代）。读屏路径的 D5 告知不像导航提示那样留一条
  `screen_reader_published` 记录（那条记录由 `prompt_outcome` 触发）；读屏会话本来就标为"完成不可判定"，这里只记下这个缺口。

### 2.11 已知局限

- **TalkBack**：发布即算说完，D5 的兜底保证只对自带 TTS 成立；读屏用户的非语音保证是进入震动（故障告警震动开着时）。
- **语音关**：没有恢复提示；周期震动停止是唯一的恢复信号。
- **只看屏幕**（语音关、两项震动都想关）：故障告警震动锁定为开，做不到完全静默（Q11a 的选择）。
- 期限 D、恢复保持 H、重试间隔没有真机校准。
- 地面告知在人多的室内常被障碍物提示冲掉；这时用户感到的是每 60 s 一次兜底震动，听到的可能只有半句。这是有意的取舍：不提高
  它的优先级（方案没有要求，也会压掉障碍物提示）。

### 2.12 JVM 验收序列

`VisionFaultAlertsTest`（纯逻辑，假时钟、假输出）至少包括：

1. 遮挡进入：立即震动 + 说 CRITICAL 告知；说完后不兜底；8 s 后重复说并震动。过暗只在进入时震动。
2. **引擎 READY 但告知一直没完成**（接收了、没有 `onSpoken`）：期限之前不重给；期限到时兜底震动（故障告警震动关着也震）并重发
   一次；同一周期最多 2 次被接收的尝试；之后每个周期期限到时再兜底，直到说完。
3. **告知被更高优先级反复冲掉**（地面：接收后被冲掉、之后一直被拒）：期限到时兜底，最多 2 次被接收的尝试。
4. **状态在兜底期间恢复**：不再兜底、不再重试；恢复提示只给一次；旧告知晚到的 `onSpoken` 被忽略。
5. 滞回：OK 闪现短于 2 s 不说恢复、不重震进入；超过 2 s 才恢复。OBSTRUCTED↔TOO_DARK 互换不说恢复、不震进入。
6. 语音关：不说；每个周期震一次（故障告警震动锁定）；不会同一周期震两下。
7. TalkBack：发布即说完，不兜底。
8. 帧质量故障期间地面轨道冻结；帧质量恢复后地面按当时状态进入或恢复。
9. 帧质量故障让未说出的恢复提示全部作废；镜头和地面在同一帧恢复时两条恢复提示都说。
10. 重试最快每 500 ms 一次。
11. 故障告警震动关、告知按时说完：全程不震。
12. 期限 D 内等描述（地面）：不打断描述；期限到时兜底震动。

另外：`SpeechManager` 的 `onSpoken` 登记（`SpokenCallbacks`，JVM）：交还后的新 id 匹配原 id、只调一次、16 个上限；
`GuidanceDelivery` 的 `vision_alerts` 分支（确认、trace 记录）；设置的生效值（语音关 → 锁定为开）；`SceneEventStringsTest`；
`EventGenerator.visionFaults` 与 `generate` 一致（含开关关掉时）。
