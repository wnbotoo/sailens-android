# 现场录制手册（阶段 2）

> 录制工具是 M0a 现场采集（见
> [`local-navigation-implementation.zh-CN.md`](local-navigation-implementation.zh-CN.md) §4），已在
> #12–#15 实现，并于 2026-09-27/28 在 SM8850（OnePlus CPH2747）和 SM8450（Samsung S22）上实测（结果见
> 实施文档 §4）。**只用基线版本录制**（第 3 节第 1 条）。

## 1. 这次录制是为了什么

这一轮录的是 **M0a 现场证据**：抽样的画面（4.3–5 Hz）、运动传感器和相机参数，外加每条提示的 trace。
它服务于：

| 用途 | 需要什么 |
|---|---|
| **误报 / 漏报基线**（阶段 2 → 阶段 3 的改动都要和它比） | 用户真正收到的每条提示 + 当时的画面 |
| **#5 地面识别门控的阈值校准** | 室内、人行道、草地边、贴墙等场景下的 `unrecognizedGroundRatio` |
| **地面几何证据**（M3） | 画面 + 重力/旋转/陀螺仪 + 相机内参，时间对齐 |
| **仿真器的场景设计**（M2），以及挑出 M0b 要重录的场景 | 每个场景的画面和提示 |

它**不能**精确回放感知。现场证据存的是抽样画面，不是 Guidance 当时依据的模型输出，所以无法据此重跑一次决策。
那是 **M0b**（模型回归记录）的事，目前还没做：第 5 节标 **回归** 的场景，要在 M0b 落地后重新录。不要把这一轮
当成可精确回放的证据。

采集在 **设置 → 诊断 → 现场采集** 里控制（只有 debug 包有）：

- **现场证据采集**（"Guidance 运行时采集"开关）：4.3–5 Hz、长边 640 px 的 JPEG + 重力、旋转、陀螺仪
  （约 47 Hz）+ 相机内参，覆盖整个 Guidance 会话。**本手册全程用这种。**
- **对时突发采集**（一次性，在同一页面开启）：以相机全帧率录约 15 秒的小尺寸画面，每台设备、每个版本测一次
  画面与陀螺仪的时间对齐。见第 6a 节。

## 2. 安全和隐私（先读）

- **录制人是明眼人，自己看路。** 应用在这里是被测对象，不是向导；它说"能走"也要自己确认。
- **过马路时注意力放在路上。** 可以继续录，但不要为了录制放慢或改变过马路的方式；不安全就停。
- 采集数据里有**人脸和地点**。只留在手机和你自己的电脑上，**不提交到任何仓库、不上传网盘**；标注
  完、不再需要的段落在采集列表里删除。
- **采集会自动清理**，有两种：
  - **按时间**：录制 7 天后删除，除非已**保留**或已导出。
  - **按容量**：总量超过 2 GB（现场证据大约只够 **3 小时**）时，先删最早的**未保留**会话——**已导出的也会删**。

  "已导出"只表示 ZIP 生成了、分享面板打开了，不代表电脑已经收到。所以：**想要的会话都点"保留"**，当天导出，
  确认 ZIP 确实到了电脑上，再在手机上"取消保留"或删除。
- 室内录制只在你有权录的地方（自己家、公司允许的区域）。

## 3. 录制前检查（每次出门前）

1. **版本是基线版本。** 录制必须用从 tag **`baseline/stage2-1`** 构建的 debug 包（该 tag 的干净 checkout；
   被忽略的 `assets/` 里的本地权重不算改动）。阶段 3 的所有改动都拿这批数据对比；混进别的版本，对比就失效了。
   每份采集都记录了构建它的 commit：`capture_stats.py` 会打印出来，它必须等于 `git rev-parse baseline/stage2-1`，
   且没有 `-dirty` 后缀。
2. **先跑一次全量真机测试，再装录制用的包。** `connectedDebugAndroidTest` 跑完会**卸载** app，所以
   顺序是：
   ```bash
   ./gradlew.bat --no-daemon connectedDebugAndroidTest
   ./gradlew.bat --no-daemon :app:installDebug
   ```
   A 仓工作区放着本地权重时，零模型相关的测试会失败，这是已知情况，记下来即可，不影响录制。
3. **打开的是对的 app。** 桌面上可能同时有 "Sailens"（官方版，B 仓）和 **"Sailens Reference"**
   （A 仓，`com.sailens.reference`）。录制用 **Sailens Reference** 的 debug 包（只有 debug 包带采集
   和 trace）。
4. **设置：**
   - 语音提醒：开；震动提醒：开（标注时能分清"听到"和"感到"）。
   - 感知挡位：**标准**（sem + det）。
   - TalkBack：关（除非这一段专门测读屏）。
   - 调试面板：开。它显示"地面识别：… （未识别 N%）"，现场就能看到 #5 门控的状态。
5. 电量 > 60%，存储余量 > 5 GB。现场证据约 **0.56–0.74 GB/小时**（SM8850 实测；户外步行 0.65），
   每次对时突发 41 MB。手机会发热，连续录 20 分钟左右休息一下，发热降频会让数据不具代表性。
6. **采集开关**（"Guidance 运行时采集"）已打开。它从下一次 Guidance 会话开始时生效，录制期间锁定。
7. **每台设备、每个版本一次**：录够 3 次可用的对时突发采集（第 6a 节）。
8. 准备一张**场景卡**（第 7 节），每段填一行。

## 4. 持机方式

整批数据里持机方式要一致，否则几何标定没法用。

- **竖屏，胸前**，镜头朝前、**略向下**，下倾约 20–30°（画面下沿大约是脚前 1–2 米的地面）。
- 离地高度大约 1.2–1.4 米；第一次录制前量一下自己的胸前高度，写在场景卡上。
- 有胸前手机支架就用，没有就双手端稳；**一段之内不要换持法**。
- 只有第 5 节 **M** 类场景故意改变持法（抬高、朝下），用来测门控的边界。

## 5. 场景清单

每类录够"次数 × 时长"。合计约 90–120 分钟，分几天录完即可，不用一次录完。标 **★** 的是 #5 阈值
校准必需的场景；标 **回归** 的场景要在 M0b 做出来后用模型回归记录重录一遍（它现在还不存在；这一轮按现场证据录）。

| 类 | 场景 | 次数 × 时长 | 要点 |
|---|---|---|---|
| A | 开阔人行道直行，人少 | 3 × 3 分钟 | 基线里的"安静"段，误报应当极少 |
| B | 人行道上有静态障碍（杆、树、停放的自行车、垃圾桶、路边椅子） | 3 × 3 分钟 | 路线上故意从障碍旁边经过，也有正对着走近再绕开 |
| C | 行人较多（商业街、地铁口） | 2 × 5 分钟 | 高峰和平峰各一次 |
| D | 路口 / 人行横道：走近、等灯、通过 | 4 个路口 | 等灯时站着不动至少 30 秒（测静止时的冷却） |
| E | 路沿、台阶、坡道：慢慢走近并停下 | 各 2 次 | **回归**；现在的模型不认台阶，这是给几何层的材料 |
| F ★ | 草地边、公园小路、土路 | 2 × 3 分钟 | terrain 不算可行走，看是否一直报"不通" |
| G ★ | 室内：走廊、大厅、家里 | 3 × 3 分钟 | 光线要足；#5 门控应当触发并播"识别不到地面…" |
| H ★ | 室内外过渡：进门、出门 | 各 4 次 | 看门控的进入（1.5 秒）和退出（1 秒）是否合理 |
| I ★ | 正对墙 / 楼体外墙：从 5 米外慢慢走近，停在墙前 1 米 | 室外 2 次、室内 2 次 | **回归**；安全关键：墙在远处时必须报"前方不通"，贴近时看门控行为 |
| J | 停车场、路边停着车 | 2 × 3 分钟 | 车辆提示是 CRITICAL，重点看误报 |
| K | 光照：夜间路灯下、强逆光 | 各 2 × 3 分钟 | 夜间会触发"光线不足"，照实录 |
| L | 站着不动（等人、聊天） | 2 × 2 分钟 | 冷却在静止时会拉长，看是否反复播报 |
| M ★ | 持法边界：故意把手机抬平 / 朝天、朝脚下 | 各 1 × 1 分钟 | 测门控在"看不到地面"时的反应 |

## 6. 每一段怎么录

采集跟着 Guidance 会话自动开始和停止，没有单独的开始/停止按钮，所以**一次"开启辅助 → 停止辅助"
就是一段**。

1. 走到起点，确认采集开关已打开，填场景卡的前半行（类别、地点类型、光线）。
2. 在应用里点"开启辅助"（采集随之开始）。
3. **对时标记：用手掌完全盖住镜头 3 秒**，听到"镜头被遮挡"后移开。它会在 trace 里留下一条
   `event_camera_blocked`，在画面里留下一段黑帧——事后用它确定这一段的起点。
4. 按场景要求走完。**现场发现漏报**（明显该提示却没提示），马上**按一下音量减键**（标记真正写入后
   会短震一下确认），或者点屏幕上的"标记漏报"按钮。它记下按键那一刻的时间和最新已存储的帧，标注时
   据此找漏报。不用看屏幕，眼睛留在路上。开着 TalkBack 也能用（已在 SM8850 上确认）。
5. 结束前再盖住镜头 3 秒，作为终点标记。
6. 点"停止辅助"（采集随之停止）。
7. 补完场景卡这一行（时长、特殊情况）。

同一段里不要切换 App、不要锁屏；中断了就停掉这一段，重新开一段。音量减键只在采集录制时被拦截，
平时照常调音量。导出 ZIP 期间 Guidance 不能启动（提示"请等采集数据导出完成后再启动 Guidance"）。

## 6a. 对时突发采集（每台设备、每个版本一次）

测量相机画面与陀螺仪在时间上的对齐，几何层需要它。它不属于基线，而且会改变设备负载，绝不要拿来做
性能数据。

1. 设置 → 诊断 → 现场采集 → **"下次启动 Guidance 时采集"**。它只对下一次启动有效：**每次突发前都要
   重新开启**。
2. 站着不动，对准几米外细节丰富的场景，光线要好。
3. 启动 Guidance 后**立即原地转动手机**：以手腕为轴，大约每秒一次快速左右转动（约 ±30°），再上下
   转动。持续约 15 秒，突发采集会自行结束，Guidance 继续运行但不再采集。
   - **端稳手机向前走不算转动。** 陀螺仪几乎测不到转动，这次突发会被判不合格（最初几次就是这样）。
   - 又慢又小的动作也会被判不合格：手机要真的转起来，而不是轻微晃动。
4. 停止 Guidance。每台设备录 3 次这样的突发。
5. 在电脑上运行 `python3 scripts/capture/timing_align.py <放采集的文件夹>`。它会列出每次突发（可用，或被拒及原因）
   和设备结果：可用突发的时延中位数及其范围。不够就重录，直到至少有 3 次可用。

## 7. 场景卡

每段一行，纸上或手机备忘录都行，事后录入表格：

| 段号 | 日期时间 | 场景类 | 地点类型（不写具体地址） | 光线 / 天气 | 持法 / 胸前高度 | 时长 | 漏报备注 | 其他 |
|---|---|---|---|---|---|---|---|---|
| 01 | 2026-10-02 10:15 | B | 小区人行道 | 晴 | 胸前 / 1.30 m | 3′10″ | 约 1′40″ 左侧矮柱没报 | |

## 8. 导出

- **trace**：设置 → 诊断 → Trace 报告 → 选中会话 → "分享 JSONL"，发到电脑上。也可以用 adb：
  `files/traces/trace_<sessionId>.jsonl`（debug 包可用 `adb shell run-as com.sailens.reference`）。
- **采集数据**（帧、传感器、内参、标记）：采集列表 → 该会话的**导出** → 系统分享，每个会话一个 ZIP。
  确认 ZIP 到了电脑之前，保持该会话"保留"（第 2 节）。用 USB 一次拉取全部采集和 trace：
  ```bash
  adb exec-out run-as com.sailens.reference tar -cf - files/captures files/traces > captures.tar
  ```
- 检查当天的录制：`python3 scripts/capture/capture_stats.py <文件夹>`（时长、存储、帧率和传感器频率、
  丢帧、计数是否对得上）。见 `scripts/capture/README.md`。
- 每段的 trace 和采集放在同一个文件夹，文件夹名用场景卡上的段号。

## 9. 标注

### 9.1 生成标注表

```bash
py scripts/export_prompt_labels.py <段号文件夹>/trace_*.jsonl -o 段号.csv
```

每一行是一条**用户真正收到的提示**（trace 里的 `prompt_outcome`，已送达的那些）。被撤回的提示用户
没听到，不可能是误报，默认不列；想看的话加 `--include-revoked`。`delivered_via` 说明它是怎么到达
用户的（`speech` 语音、`screen_reader` 读屏、`haptics` 震动、`status_card` 状态卡片）：只有 `haptics`
的提示是"感到"而不是"听到"，即使当时语音是开着的。`output_settings` 只作背景。表里还附带了那一帧的
地面识别状态、是否判为阻塞、跟踪到的障碍物和主要类别，方便对照。

### 9.2 逐条打标签

对照这条提示前后几秒的画面，在 `label` 列填。看画面在电脑上做（手机上没有查看器）：

```bash
python3 scripts/capture/contact_sheet.py <采集文件夹> --trace <trace>.jsonl --prompts --window 2
python3 scripts/capture/contact_sheet.py <采集文件夹> --markers --window 3
```

每条提示一张 PNG，以提出它的那一帧的**时间戳**为中心（来自 trace，精确），标题写明提示内容和送达方式。
现场证据只存抽样画面（4.3–5 Hz），所以那一帧的图像常常没有存下：高亮的是离它最近的已存储帧，最多可能差约
0.12 秒——判断 `late` 或快速移动的障碍物时要记住这一点。标题里的送达延迟（"… ms after the frame"）只有
在提出提示的那一帧恰好被存下时才会显示。每个漏报标记一张，以观察到按键的时刻为中心。

| 标签 | 含义 |
|---|---|
| `tp` | 属实，而且对行走有意义 |
| `fp` | 前方没有这回事，或者有但不值得提示（例如很远、不在路线上的人） |
| `wrong` | 有这回事，但说错了（方位错、类别错） |
| `late` | 属实但太晚（已经走到跟前才报） |
| `unsure` | 看画面也判断不了；在 `note` 写原因 |

### 9.3 漏报

另建一张表 `段号_misses.csv`，每个漏报一行：`段号, 大约时间（进入这一段第几秒）, 漏了什么, 距离估计, 备注`。
来源有两个：现场按音量减键留下的标记（第 6 节第 4 步；每个标记都要在表里有一行，确认后填内容，
误按的标 `误按`），以及回看画面时发现的"明显该报却没报"。漏报的判定标准：路线上
约 2 米以内的障碍物、真实走不通的路径、或者台阶/路沿，在走到跟前之前没有任何提示。

### 9.4 标注一致性

标注有主观成分。前 3 段标完后，隔一天自己再标一遍同样的 3 段，两次结果差异超过 10% 的标签类别，
把判定标准补写到本节，然后再继续。

## 10. 这批数据怎么用（给后续开发）

- **基线指标**：按提示类别统计 `fp / 已送达` 和漏报数，作为阶段 3 的对比基准。统计脚本随阶段 3 提供。
- **#5 阈值**：F、G、H、I、M 类的 `unrecognizedGroundRatio` 分布决定进入/退出阈值和确认时长；A、B 类
  用来确认室外不会误触发。
- **几何**：用采集工具（`scripts/capture/`）读取，见实施文档 §4。**回放**决策需要 M0b 的记录，不是这一轮的数据。
